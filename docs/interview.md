# 简历与面试：用证据展示能力

## 1. 这个项目能展示什么

对 Python 后端应届生，项目价值在于能把一个业务流程做完整，并能解释权限、数据库一致性、异步处理和失败行为。使用多少框架不等于工程深度。代码由工具辅助生成时，应如实描述，独立完成并理解自己的改造和验证。

当前可讲的主题包括 FastAPI 接口、Argon2/JWT、SQLAlchemy 约束、文档异步入库、任务租约与幂等、RAG 检索、SSE、模型适配、Alembic 和自动化检查。Docker 与真实模型的实际验证状态要单独说明。

## 4. 高频追问与回答线索

**为什么用后台任务，而不是接口里直接解析 PDF？**

解析可能占用 CPU，向量服务有网络延迟。接口保存必要数据后返回任务 ID，后台处理能独立限制并发与重试。local 的线程池方便调试，Celery 的独立进程和持久队列更接近部署场景。

**Celery 已经保证投递，为什么还需要数据库状态和租约？**

任务可能重复投递，Worker 也可能在确认前崩溃。数据库状态记录业务事实，租约 token 阻止超时旧 Worker 发布结果，唯一约束和事务保证最终数据一致。它是至少一次投递配合幂等，不是 exactly-once。

**用户删除文件时后台恰好完成怎么办？**

删除先写入不可见状态，检索立即排除；最终入库事务再次检查删除状态、文档版本和任务租约。物理文件清理不决定访问权限。已有会话中的历史引用快照不会自动抹除。

**为什么使用 pgvector，没有单独上向量数据库？**

当前规模下可以把业务数据和向量放在 PostgreSQL 中，便于一致性和权限过滤。代码使用精确距离搜索，没有 HNSW。等测出数据规模与延迟瓶颈后，再讨论近似索引或独立服务，不能用框架选择代替性能证据。

**为什么模型换了后必须重新生成文档向量？**

不同模型的向量空间不一致；相同维度也不代表可比较。系统保存配置指纹并在检索中过滤；PostgreSQL 维度变化还需要表结构变更。

**检索命中率高是不是回答准确率高？**

不是。命中率表示证据是否被检索到；模型可能误读证据，引用也可能不支持结论。需分别评估检索、人工事实支持、无答案问题和延迟。当前离线评测不会冒充真实生成质量。

**如何防止文档中的提示词注入？**

先用后端鉴权和 SQL 过滤限制可见数据，再将文档作为不可信材料提供给模型。系统不向模型开放数据库或执行工具。提示词要求不能彻底消除幻觉或注入风险，更不能替代权限检查。

**流式回答出错，为什么不直接自动重试？**

已经返回的文字无法撤回，新请求可能重复计费，拼接不同回答会产生错误。系统明确标注错误和不完整状态，客户端依据 SSE 事件处理；不会把部分响应当作完整成功。

**Redis 限流是否等于全局生成并发控制？**

不是。Redis 计数限制请求频率，生成并发上限目前按 API 进程控制；多副本的总并发会随进程数量扩大。要实现全局配额，需要独立的分布式租约或调度方案。

**如何证明自己真的理解？**

给出一处自己修改的代码、触发问题的最小输入、修复前失败的测试和修复后的结果；解释为什么选择该方案及它仍有哪些限制，比复述架构名词更有说服力。

## 5. 面试前自查

- 能从请求进入到数据库/模型响应完整跟踪一次调用。
- 能说明至少三个数据库约束和两个关键事务边界。
- 能现场演示正常流程、越权被拒绝以及一次可恢复失败。
- 能区分真实调用、模拟上游测试和离线基线。
- 评测数字有运行文件、配置、题集和日期可核对。
- 清楚哪些功能尚未实现，不把下一步计划写成已有成果。
